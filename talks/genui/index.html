THE TOOL

Generative UI, with the GenUI SDK

Generative UI means the model answers with a small screen instead of a paragraph: cards, chips, a form. In Flutter you do it with genui, a package from the Flutter team on pub.dev.

The widgets are yours, so they look like your app. The model only decides which ones to show.

⚠︎ The package calls itself "highly experimental". This talk uses genui 0.10.4. The API has changed a lot this year, so pin your version.

THE WHOLE MODEL

Three ideas. That's it.

01

You choose the widgets

The model can only use widgets you register in a catalog. If a widget isn't in it, it can't appear.

02

It sends a description

The model describes the screen in JSON. Your app turns that into real Flutter widgets.

03

Taps go back to it

When someone taps or picks something, the model hears about it and can answer with the next screen.

THE PROTOCOL UNDERNEATH

A2UI: a shared language for UI

(Agent-to-User Interface)

The model sends a description of the screen. Your app reads it and draws it with its own widgets, so the model never runs code inside your app. The same messages can be drawn by Flutter, React, Angular or Lit.

WHAT'S ACTUALLY IN THE JSON

The model can send four kinds of message.

createSurface

Start a new screen.

updateComponents

Add or change the widgets on it.

updateDataModel

Change the values those widgets show.

deleteSurface

Take a screen away.

an A2UI message, shortened
{"updateComponents": {"surfaceId": "s2", "components": [
  {"id": "root", "component": "Column", "children": ["card1", "card2"]},
  {"id": "card1", "component": "RecipeCard",
   "recipeId": "paneer_bhurji", "reason": "Ready in 15 minutes with your paneer."},
  …
]}}

A flat list of widgets. A parent points at its children by id. This is A2UI v0.9, the version genui speaks.

WHAT JUST HAPPENED

The app owns the facts.
The model owns the words.

It could only pick from the 20 recipes in my app. Cook times, ingredient amounts and photos all came from my data. The model wrote the parts that are words: the reason on each card, and the new steps when I asked for it spicier.

And it looks like Sage, not like Gemini, because genui's built-in widgets use my app's theme.

THE BUILDING BLOCKS

How it fits together.

Follow one turn from top to bottom. Each piece hands off to the next, then it loops back.

1
Conversation
Runs the turn loop between the person, the model and the screen.
2
A2uiTransportAdapter
Takes the model's streamed text and pulls the A2UI messages out of it.
3
Catalog
The only widgets the model is allowed to use.
CatalogItemname·dataSchema·widgetBuilder
4
SurfaceController + Surface
Holds every generated screen. A Surface widget draws one of them.
5
DataModel
The values the widgets show. When someone taps, an action goes…
↺ …back to the Conversation, and the next turn starts.
THE PROMPT I WROTE

You steer it with the prompt.

recipe_prompts.dart (3 of my 7 instructions, trimmed)
// The flow
'ALWAYS follow this exact flow and never skip a step:
 (1) gather ingredients, time and number of people using input components;
 (2) show multiple recipe cards to choose from;
 (3) only after the user taps a card, show that full recipe.'

// The facts stay mine: the app fills in this list from its own data
'Reference recipes ONLY by an id from this list, and NEVER invent an id:
 - tomato_paneer_masala: Tomato Paneer Masala (20 min, medium; …)
 - …'

// A way out
'If the user asks for something none of those recipes reasonably satisfy
 (for example a burger…), do NOT force an unrelated recipe. Instead, briefly
 and warmly say you don't have that recipe yet…'

Plain English. genui's PromptBuilder wraps it with the A2UI rules and the schema of every widget in my catalog. All together that's about 16k tokens, and it goes out with every request.

CODE 01 — THE CONTRACT

A widget the model is allowed to use

recipe_card.dart (trimmed)
final recipeCardItem = CatalogItem(
  name: 'RecipeCard',
  // It takes an id, not a title or a cook time.
  // The model can point at one of my recipes. It can't make one up.
  dataSchema: S.object(
    properties: {
      'recipeId': S.string(),
      'reason': A2uiSchemas.stringReference(), // the only free text
    },
    required: ['recipeId'],
  ),
  widgetBuilder: (itemContext) {
    final data = itemContext.data as JsonMap;
    return RecipeLookup(                // finds the id in my data
      dataContext: itemContext.dataContext,
      recipeId: data['recipeId'],
      builder: (context, recipe) => /* my card widget */,
    );
  },
);

Name, schema, builder. If the model sends an id I don't have, the card says "Unknown recipe" instead of showing something made up.

CODE 03 — LOGIC THAT RUNS ON THE PHONE

Some taps never reach the model.

from the model: bind servings
{"component": "RecipeView",
 "recipeId": "dal_tadka",
 "servings": {"path": "/servings"}}

// my stepper writes the value
dataContext.update(
  DataPath(servingsPath), value);
from the model: check and format
"checks": [{"condition": {"call": "numeric",
  "args": {"value": {"path": "/servings"},
           "min": 1, "max": 12}},
  "message": "Between 1 and 12 people"}]

"text": {"call": "formatString", …
  "Cooking for ${/servings} ${pluralize(…)}"}

The model wires widgets to values once. After that the phone does the work. numeric, formatString and pluralize are functions registered in genui's basic catalog, so the model can call them but can't invent new ones.

FIG. 03 — WHAT I LEARNED

Four things I learned
the hard way.

They only came up once I used the app for real.

LESSON 01

Not every tap needs the model.

Changing servings, or typing how many people you're cooking for, never calls Gemini. The phone does the maths and the checks.

It's instant, and it doesn't cost a request.

LESSON 02

Models make mistakes. Check before you show.

Sometimes the model forgets a widget, or uses one that isn't in the catalog. Sage checks each screen before showing it. If something's missing, it holds the screen back, tells the model what's wrong, and shows the fixed one.

In this clip I break the reply on purpose with a debug button, so you can watch the repair.

LESSON 03

Teach it to say no.

If the model can only use your data, it needs a way out. Ask Sage for a burger and it tells you it doesn't have one, instead of pushing paneer at you.

That took a few lines in the prompt.

LESSON 04

Every turn has a cost.

Every request sends that 16k-token prompt again. My free-tier project allowed 250,000 input tokens a minute. That's only about 15 requests, and I hit it often while testing.

The cheapest fix is doing small things on the phone, like servings and validation. After that, choose your plan with this in mind.

WHERE THIS IS HEADED · OCT 2026

genui is being split up.

Today: genuiAnnounced: a2ui_core · a2ui_agent · a2ui_flutter
ShapeOne package does it all: prompt, parsing, conversation, renderingThree packages: the protocol, the agent side (prompt and parsing), and the Flutter renderer
StatusOn pub.dev, 0.10.4Early. a2ui_core is 0.3.0. The agent and Flutter packages are pre-releases, and a2ui_flutter is installed from GitHub for now
A2UIv0.9a2ui_core reads v0.9 up to v1.0. The agent and Flutter packages speak v0.9 for now
Your codeWhat you saw todayA different API, so expect to migrate

A2UI itself is moving too. v0.9.1 is the current release, and v1.0 is a release candidate: the app and the model can call each other's functions, and one screen can mix widgets from several catalogs.

A RULE OF THUMB

When to reach for it.

Great fit

The right screen depends on what the person wants: exploring, comparing, narrowing things down, or making sense of a photo.

Probably overkill

A settings page, a login form, a checkout flow you already know. A well-designed fixed screen still wins there.

Use it where you can't predict which screen someone needs.
